# File in Image — APP_SPEC.md

## 1. Product identity

- **Name:** File in Image
- **Japanese name:** 画像にファイルを埋め込む
- **Slug:** `file-in-image`
- **Current version:** v0.4.0
- **Repository:** `ttomohisa/htmlapps-file-in-image`
- **One-sentence purpose:** Hide one arbitrary file inside image pixels and recover the original bytes later without uploading either file.
- **Release artifacts:** `dist/index.html`, `dist/index.self-extract.html`, and the generated repository-root `file-in-image.html`.

## 2. Problem and outcome

The app lets a user select a carrier image and one payload file, optionally protect the payload with a password, produce a PNG containing the payload, then recover the original file from that PNG. User-selected images, files, and passwords stay inside the browser.

v0.4.0 adds password protection while preserving the v0.2.0/v0.3.0 sequential embedding format for backward compatibility.

## 3. Current core flow (v0.4.0)

### Embed

1. Select or drop a PNG, JPEG, or WebP carrier image.
2. Select or drop one arbitrary payload file up to 32 MiB.
3. The app packs filename, MIME, SHA-256, and file bytes into BKFC.
4. The complete BKFC container is GZIP-compressed only when the result is smaller.
5. Optionally enable password protection and enter the password twice.
6. When password protection is enabled, PBKDF2-HMAC-SHA-256 derives key material and AES-256-GCM encrypts the compressed or uncompressed BKFC body.
7. Capacity is checked against the exact stored body length, including the AES-GCM authentication tag when encrypted.
8. The app embeds the BKFI outer header and stored body in RGB least-significant bits and creates a PNG.
9. Edit the suggested output basename and save the PNG.

### Extract

1. Select or drop a PNG generated by this app.
2. The app reads the BKFI header before attempting to parse inner metadata.
3. If the encrypted flag is present, the password field is shown.
4. The body is authenticated/decrypted with AES-256-GCM.
5. If the GZIP flag is present, the decrypted body is decompressed.
6. The BKFC container is parsed and the recovered payload SHA-256 is verified.
7. Edit the recovered filename if needed and save the file.

## 4. Current format status

v0.4.0 remains a development format and **is not the final v1 compatibility freeze**.

- BKFI outer header: 80 bytes.
- Development `formatVersion`: `0`.
- Development `embeddingMode`: `0` (sequential opaque-pixel RGB LSB).
- BKFC inner fixed header: 48 bytes.
- GZIP: implemented for the complete BKFC container.
- Password KDF: PBKDF2-HMAC-SHA-256.
- Encryption: AES-256-GCM.
- Payload integrity after recovery: SHA-256 of original file bytes.
- Adaptive embedding: not implemented yet.

The final v1 format/version must not be frozen before adaptive-placement and cross-browser tests pass.

## 5. BKFI outer header — 80 bytes

All integer fields are big-endian.

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFI` |
| 4 | 1 | format version (`0`) |
| 5 | 1 | embedding mode (`0`) |
| 6 | 1 | flags |
| 7 | 1 | KDF ID |
| 8 | 2 | header length (`80`) |
| 10 | 2 | reserved (`0`) |
| 12 | 4 | stored body length |
| 16 | 4 | PBKDF2 iteration count |
| 20 | 16 | PBKDF2 salt |
| 36 | 12 | AES-GCM IV |
| 48 | 16 | placement salt (reserved until the adaptive-placement milestone) |
| 64 | 16 | reserved |

Flags:

- bit 0: AES-GCM encrypted body
- bit 1: GZIP-compressed inner body
- bits 2–7: reserved

KDF IDs:

- `0`: none
- `1`: PBKDF2-HMAC-SHA-256

v0.2.0/v0.3.0 images have no encrypted flag and remain readable.

## 6. BKFC inner container

The fixed header remains 48 bytes:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFC` |
| 4 | 1 | container version (`0`) |
| 5 | 1 | reserved |
| 6 | 2 | fixed header length (`48`) |
| 8 | 2 | UTF-8 filename byte length |
| 10 | 2 | UTF-8 MIME byte length |
| 12 | 4 | original file byte length |
| 16 | 32 | SHA-256 of original file bytes |

Then filename bytes, MIME bytes, and original file bytes follow.

When password protection is enabled, the entire BKFC container is inside the encrypted body, so filename and MIME are not readable without successful authentication/decryption.

## 7. Compression

- Compression target: the complete BKFC container.
- Algorithm: GZIP through `CompressionStream("gzip")`.
- GZIP is adopted only when it is smaller than the uncompressed BKFC container.
- Compression happens before encryption.
- Extraction decrypts before GZIP decompression.
- Decompression output is bounded while streaming.
- Compression is an efficiency feature, not a security feature.

## 8. Password protection and cryptography

### Password input

- Password protection is optional.
- Embed requires password + confirmation when enabled.
- The password is not trimmed or Unicode-normalized before UTF-8 encoding.
- Passwords are never written to localStorage, IndexedDB, URL parameters, filenames, logs, analytics, or telemetry.
- Extract only asks for a password when the BKFI encrypted flag is present.

### KDF

- PBKDF2-HMAC-SHA-256.
- Default work factor: 600,000 iterations.
- 16 random salt bytes from `crypto.getRandomValues()`.
- The iteration count is stored in the BKFI header for decode compatibility.
- Development-format decoding bounds accepted PBKDF2 iterations to a sane range before starting expensive work.

### AES-GCM

- AES key size: 256 bits.
- IV: 12 random bytes from `crypto.getRandomValues()`.
- Authentication tag: 128 bits.
- The complete 80-byte BKFI header is supplied as AES-GCM Additional Authenticated Data.
- The stored encrypted body length includes the 16-byte GCM tag.
- Wrong passwords, modified ciphertext, or authenticated-header changes must not produce recovered metadata or file bytes.

## 9. Current embedding algorithm

- Only pixels with `alpha === 255` are eligible.
- Alpha is never modified.
- Header and body use R, G, B in that order.
- Exactly one least-significant bit is used per channel.
- The first 214 eligible opaque pixels are reserved for the 640-bit BKFI header.
- The body starts at eligible opaque pixel 214.
- The image is exported as PNG through Canvas.
- Input image container metadata is not carried into the generated PNG.

## 10. Limits

- Carrier input: PNG, JPEG, WebP.
- Output: PNG only.
- Payload: one arbitrary file.
- Payload hard limit: 32 MiB before container/compression/encryption.
- Carrier maximum: 32,000,000 pixels, maximum width/height 8192 px.
- Carrier must contain at least 214 fully opaque pixels plus enough body slots.
- No automatic carrier upscaling.

## 11. Data and privacy

- Carrier image, payload bytes, passwords, recovered bytes, and generated PNG stay inside browser memory unless the user explicitly saves a file.
- File bytes and passwords are not persisted in localStorage or IndexedDB.
- Only non-sensitive UI preferences such as language may be stored locally.
- No analytics, telemetry, remote fonts, CDN, API, or runtime fetch is allowed.
- CSP keeps `connect-src 'none'`.

## 12. UX and accessibility

- Japanese / English in the same HTML.
- Password protection is presented as an optional user-facing step without exposing unnecessary KDF jargon in the primary flow.
- Original file size, exact stored-body size, compression state, image capacity, and fit state remain visible.
- Enabling encryption accounts for the GCM authentication tag before enabling Embed.
- Password mismatch is shown before processing starts.
- Encrypted extraction shows a password field only after reading an encrypted BKFI header.
- Wrong-password/authentication failures use a clear combined message because the app cannot distinguish them safely from authenticated-data modification.
- Desktop and smartphone are first-class; 360 px width must not create horizontal scrolling.
- Status changes use `aria-live` and keyboard focus remains visible.

## 13. Browser target

Current stable desktop/mobile Chromium, Firefox, and Safari. Direct `file://` opening is required.

Required for full v0.4.0 behavior:

- Canvas / ImageData
- Web Crypto: SHA-256, PBKDF2, AES-GCM
- `crypto.getRandomValues()`
- Blob / Object URL
- File API
- CompressionStream / DecompressionStream for GZIP

## 14. v0.4.0 acceptance criteria

- All v0.2.0 and v0.3.0 unencrypted images remain readable.
- Password protection can be enabled or left off.
- Embed is blocked when enabled password fields are empty or do not match.
- The exact password string is used; no trimming or normalization is applied.
- PBKDF2-HMAC-SHA-256 uses 600,000 iterations and a random 16-byte salt.
- AES-256-GCM uses a random 12-byte IV and 128-bit tag.
- Filename, MIME, SHA-256, and payload bytes are all inside the encrypted body.
- The complete BKFI header is authenticated as AAD.
- Encrypted capacity calculation includes the 16-byte GCM tag before processing.
- Correct password recovers the exact payload and original metadata.
- Wrong password is rejected before metadata is displayed.
- Modified ciphertext or authenticated-header values fail authentication or structural validation.
- GZIP + encryption and no-GZIP + encryption both round-trip correctly.
- Runtime external network access remains zero.
- No third-party runtime dependency is introduced.

## 15. Roadmap after v0.4.0

- **v0.5.0:** deterministic 8×8 adaptive embedding, LSB-independent detail ranking, randomized placement.
- **v0.6.0:** Worker, progress/cancel, stale-result protection, memory regression.
- **v0.7.0:** mandatory generated-PNG self-verification.
- **v0.8.0:** UI/mobile/accessibility polish.
- **v0.9.0:** release candidate and cross-browser format freeze.
- **v1.0.0:** stable release; no new scope beyond RC fixes.

## In-app help

The header help dialog must describe the actual current password/GZIP behavior and limitations. It must not advertise adaptive embedding or generated-PNG self-verification before those features exist.
