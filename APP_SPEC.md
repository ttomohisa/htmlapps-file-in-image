# File in Image — APP_SPEC.md

## 1. Product identity

- **Name:** File in Image
- **Japanese name:** 画像にファイルを埋め込む
- **Slug:** `file-in-image`
- **Current version:** v0.2.0
- **Repository:** `ttomohisa/htmlapps-file-in-image`
- **One-sentence purpose:** Hide one arbitrary file inside image pixels and recover the original bytes later without uploading either file.
- **Release artifacts:** `dist/index.html`, `dist/index.self-extract.html`, and the generated repository-root `file-in-image.html`.

## 2. Problem and outcome

The app lets a user select a carrier image and one payload file, produce a PNG containing the payload, then recover the payload from that PNG. User-selected data stays inside the browser. The v0.2.0 implementation establishes the binary container and a deterministic sequential 1-bit LSB transport before the v1 adaptive/encrypted format is frozen.

## 3. Current core flow (v0.2.0)

### Embed

1. Select or drop a PNG, JPEG, or WebP carrier image.
2. Select or drop one arbitrary payload file up to 32 MiB.
3. Review carrier dimensions, opaque-pixel capacity, payload size, and fit status.
4. Run Embed.
5. The app packs the payload into the BKFC development container, computes SHA-256, embeds BKFI + BKFC bytes in RGB least-significant bits, and creates a PNG.
6. Edit the suggested output basename and save the PNG.

### Extract

1. Select or drop a PNG generated by this app.
2. The app reads the BKFI header and BKFC container.
3. It verifies the recovered payload SHA-256.
4. Edit the recovered filename if needed and save the file.

## 4. Current format status

v0.2.0 is a development format and **not the final v1 compatibility freeze**.

- BKFI outer header: 80 bytes.
- Development `formatVersion`: `0`.
- Development `embeddingMode`: `0` (sequential opaque-pixel RGB LSB).
- BKFC inner fixed header: 48 bytes.
- Payload integrity: SHA-256 of original file bytes.
- Encryption: not implemented yet.
- GZIP: not implemented yet.
- Adaptive embedding: not implemented yet.

The final v1 format/version must not be frozen before cross-browser adaptive-placement tests pass.

## 5. Binary layout used by v0.2.0

All integer fields are big-endian.

### BKFI outer header — 80 bytes

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFI` |
| 4 | 1 | format version (`0`) |
| 5 | 1 | embedding mode (`0`) |
| 6 | 1 | flags (`0`) |
| 7 | 1 | KDF ID (`0`) |
| 8 | 2 | header length (`80`) |
| 10 | 2 | reserved (`0`) |
| 12 | 4 | BKFC body length |
| 16..79 | 64 | reserved for future v1 crypto/placement fields |

### BKFC inner container

Fixed header is 48 bytes:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFC` |
| 4 | 1 | container version (`0`) |
| 5 | 1 | reserved |
| 6 | 2 | fixed header length (`48`) |
| 8 | 2 | UTF-8 filename byte length |
| 10 | 2 | UTF-8 MIME byte length |
| 12 | 4 | original file byte length |
| 16 | 32 | SHA-256 of original file bytes |

Then filename bytes, MIME bytes, and original file bytes follow.

## 6. Current embedding algorithm

- Only pixels with `alpha === 255` are eligible.
- Alpha is never modified.
- Header and body use R, G, B in that order.
- Exactly one least-significant bit is used per channel.
- The first 214 eligible opaque pixels are reserved for the 640-bit BKFI header.
- The BKFC body starts at eligible opaque pixel 214.
- The image is exported as PNG through Canvas.
- Metadata from the input container is not carried into the generated PNG.

## 7. Limits

- Carrier input: PNG, JPEG, WebP.
- Output: PNG only.
- Payload: one arbitrary file.
- Payload hard limit: 32 MiB.
- Carrier maximum: 32,000,000 pixels, maximum width/height 8192 px.
- Carrier must contain at least 214 fully opaque pixels plus enough body slots.
- No automatic carrier upscaling.

## 8. Data and privacy

- Carrier image, payload bytes, recovered bytes, and generated PNG remain in browser memory unless the user explicitly saves a file.
- File bytes are not persisted in `localStorage` or IndexedDB.
- Only non-sensitive UI preferences such as language may be stored locally.
- No analytics, telemetry, remote fonts, CDN, API, or runtime fetch is allowed.
- CSP keeps `connect-src 'none'`.

## 9. UX and accessibility

- Japanese / English in the same HTML.
- Light-only interface.
- Desktop and smartphone are first-class.
- 360 px width must not create horizontal scrolling.
- Drop zones also provide standard file buttons.
- Long filenames wrap/truncate without breaking layout.
- Processing/error/result states are separate.
- Status changes use `aria-live`.
- Keyboard focus remains visible.
- Help explains that editing, resizing, converting, or recompressing the generated PNG can destroy the hidden data.

## 10. Browser target

Current stable desktop/mobile Chromium, Firefox, and Safari. Direct `file://` opening is required.

Required in v0.2.0:

- Canvas / ImageData
- Web Crypto SHA-256
- Blob / Object URL
- File API

## 11. v0.2.0 acceptance criteria

- PNG/JPEG/WebP carriers load and preview.
- Arbitrary payload files up to 32 MiB load.
- Capacity is calculated from fully opaque pixels only.
- Too-large payloads are blocked before encoding.
- Generated PNG can be opened again and the original payload is recovered byte-for-byte.
- Recovered SHA-256 must match before Save is enabled.
- Plain images are rejected as non-BKFI.
- Malformed lengths are rejected without large allocations.
- Output basename is editable and `.png` is fixed separately.
- Recovered filename is editable before save.
- Runtime external network access is zero.
- No third-party runtime dependency is required.

## 12. Roadmap after v0.2.0

- **v0.3.0:** GZIP via Compression Streams and exact post-compression capacity UI.
- **v0.4.0:** PBKDF2-HMAC-SHA-256 + AES-256-GCM, encrypted filename/MIME, AAD.
- **v0.5.0:** deterministic 8×8 adaptive embedding, LSB-independent detail ranking, randomized placement.
- **v0.6.0:** Worker, progress/cancel, stale-result protection, memory regression.
- **v0.7.0:** mandatory generated-PNG self-verification.
- **v0.8.0:** UI/mobile/accessibility polish.
- **v0.9.0:** release candidate and cross-browser format freeze.
- **v1.0.0:** stable release; no new scope beyond RC fixes.

## In-app help

The header help dialog must describe the actual currently implemented behavior and limitations. It must not advertise encryption, GZIP, adaptive embedding, or self-verification before those features exist.
