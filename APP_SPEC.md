# File in Image — APP_SPEC.md

## 1. Product identity

- **Name:** File in Image
- **Japanese name:** 画像にファイルを埋め込む
- **Slug:** `file-in-image`
- **Current version:** v0.3.0
- **Repository:** `ttomohisa/htmlapps-file-in-image`
- **One-sentence purpose:** Hide one arbitrary file inside image pixels and recover the original bytes later without uploading either file.
- **Release artifacts:** `dist/index.html`, `dist/index.self-extract.html`, and the generated repository-root `file-in-image.html`.

## 2. Problem and outcome

The app lets a user select a carrier image and one payload file, produce a PNG containing the payload, then recover the payload from that PNG. User-selected data stays inside the browser.

v0.3.0 adds GZIP compression to the development format. The complete BKFC container is compressed only when the GZIP result is smaller, so the capacity UI can show the exact number of body bytes that will be embedded.

## 3. Current core flow (v0.3.0)

### Embed

1. Select or drop a PNG, JPEG, or WebP carrier image.
2. Select or drop one arbitrary payload file up to 32 MiB.
3. The app packs filename, MIME, SHA-256, and file bytes into BKFC.
4. If `CompressionStream("gzip")` is available, the app GZIP-compresses the BKFC container and adopts it only when it is smaller.
5. Review image capacity, original file size, exact embedded-body size, compression state, and fit status.
6. Run Embed.
7. The app stores BKFI + body bytes in RGB least-significant bits and creates a PNG.
8. Edit the suggested output basename and save the PNG.

### Extract

1. Select or drop a PNG generated by this app.
2. The app reads the BKFI header and body.
3. If the BKFI GZIP flag is set, the body is decompressed with `DecompressionStream("gzip")`.
4. The BKFC container is parsed and the recovered payload SHA-256 is verified.
5. Edit the recovered filename if needed and save the file.

## 4. Current format status

v0.3.0 is a development format and **not the final v1 compatibility freeze**.

- BKFI outer header: 80 bytes.
- Development `formatVersion`: `0`.
- Development `embeddingMode`: `0` (sequential opaque-pixel RGB LSB).
- BKFC inner fixed header: 48 bytes.
- Payload integrity: SHA-256 of original file bytes.
- GZIP: implemented for the complete BKFC container.
- Encryption: not implemented yet.
- Adaptive embedding: not implemented yet.

The final v1 format/version must not be frozen before cross-browser adaptive-placement tests pass.

## 5. Binary layout used by v0.3.0

All integer fields are big-endian.

### BKFI outer header — 80 bytes

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFI` |
| 4 | 1 | format version (`0`) |
| 5 | 1 | embedding mode (`0`) |
| 6 | 1 | flags |
| 7 | 1 | KDF ID (`0`) |
| 8 | 2 | header length (`80`) |
| 10 | 2 | reserved (`0`) |
| 12 | 4 | stored body length |
| 16..79 | 64 | reserved for future v1 crypto/placement fields |

Current flags:

- bit 0: reserved for encryption
- bit 1: GZIP-compressed body
- bits 2–7: reserved

A v0.2.0 image has flags `0` and remains readable in v0.3.0.

### BKFC inner container

Fixed header is 48 bytes:

| Offset | Size | Field |
| ---: | ---: | --- |
| 0 | 4 | ASCII `BKFC` |
| 4 | 1 | container version (`0`) |
| 5 | 1 | reserved |
| 6 | 2 | fixed header length (`48`) |
| 8 | 2 | UTF-8 filename byte length |
| 10 | 2 | UTF-8 MIME byte length |
| 12 | 4 | original file byte length |
| 16 | 32 | SHA-256 of original file bytes |

Then filename bytes, MIME bytes, and original file bytes follow.

## 6. Compression

- Compression target: the complete BKFC container.
- Algorithm: GZIP through the browser-native Compression Streams API.
- GZIP is adopted only when `gzipBytes < bkfcBytes`.
- If CompressionStream is unavailable while embedding, the app falls back to an uncompressed body.
- If an image is marked GZIP-compressed, extraction requires DecompressionStream.
- Decompression is streamed with a byte-count limit so malformed input cannot expand without bound.
- Compression is an efficiency feature, not a security feature.

## 7. Current embedding algorithm

- Only pixels with `alpha === 255` are eligible.
- Alpha is never modified.
- Header and body use R, G, B in that order.
- Exactly one least-significant bit is used per channel.
- The first 214 eligible opaque pixels are reserved for the 640-bit BKFI header.
- The body starts at eligible opaque pixel 214.
- The image is exported as PNG through Canvas.
- Metadata from the input container is not carried into the generated PNG.

## 8. Limits

- Carrier input: PNG, JPEG, WebP.
- Output: PNG only.
- Payload: one arbitrary file.
- Payload hard limit: 32 MiB before container/compression.
- Carrier maximum: 32,000,000 pixels, maximum width/height 8192 px.
- Carrier must contain at least 214 fully opaque pixels plus enough body slots.
- No automatic carrier upscaling.

## 9. Data and privacy

- Carrier image, payload bytes, recovered bytes, and generated PNG remain in browser memory unless the user explicitly saves a file.
- File bytes are not persisted in `localStorage` or IndexedDB.
- Only non-sensitive UI preferences such as language may be stored locally.
- No analytics, telemetry, remote fonts, CDN, API, or runtime fetch is allowed.
- CSP keeps `connect-src 'none'`.

## 10. UX and accessibility

- Japanese / English in the same HTML.
- Light-only interface.
- Desktop and smartphone are first-class.
- 360 px width must not create horizontal scrolling.
- Drop zones also provide standard file buttons.
- Long filenames must not break layout.
- Original file size, exact stored-body size, compression state, image capacity, and fit state are visible before embedding.
- Processing/error/result states are separate.
- Status changes use `aria-live`.
- Keyboard focus remains visible.
- Help explains that editing, resizing, converting, or recompressing the generated PNG can destroy the embedded data.

## 11. Browser target

Current stable desktop/mobile Chromium, Firefox, and Safari. Direct `file://` opening is required.

Required for the full v0.3.0 flow:

- Canvas / ImageData
- Web Crypto SHA-256
- Blob / Object URL
- File API
- CompressionStream for GZIP creation
- DecompressionStream for GZIP recovery

Embedding degrades to uncompressed storage if CompressionStream is unavailable.

## 12. v0.3.0 acceptance criteria

- All v0.2.0 embed/extract behavior remains available.
- v0.2.0 images with flags `0` remain readable.
- Compressible BKFC data is stored as GZIP when and only when it is smaller.
- Already-compressed/incompressible data is stored without GZIP when GZIP is not smaller.
- Capacity UI uses the actual stored body length, not an estimate.
- Original size, stored size, and compression decision are visible before embedding.
- GZIP flag is written and interpreted consistently.
- GZIP bodies are decompressed before BKFC parsing.
- Decompression output is bounded before allocation/copy completion.
- Recovered SHA-256 must match before Save is enabled.
- Runtime external network access remains zero.
- No third-party runtime dependency is introduced.

## 13. Roadmap after v0.3.0

- **v0.4.0:** PBKDF2-HMAC-SHA-256 + AES-256-GCM, encrypted filename/MIME, AAD.
- **v0.5.0:** deterministic 8×8 adaptive embedding, LSB-independent detail ranking, randomized placement.
- **v0.6.0:** Worker, progress/cancel, stale-result protection, memory regression.
- **v0.7.0:** mandatory generated-PNG self-verification.
- **v0.8.0:** UI/mobile/accessibility polish.
- **v0.9.0:** release candidate and cross-browser format freeze.
- **v1.0.0:** stable release; no new scope beyond RC fixes.

## In-app help

The header help dialog must describe the actual currently implemented behavior and limitations. It must not advertise encryption, adaptive embedding, or self-verification before those features exist.
